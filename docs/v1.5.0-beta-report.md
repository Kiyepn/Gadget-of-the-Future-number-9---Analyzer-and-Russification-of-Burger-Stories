# Отчёт: v1.5.0-beta (Lightweight) — Windows Native OCR

Ветка: `feat/v1.5.0-beta-lightweight` · сборка локальная, **на GitHub ничего не
публиковалось и не пушилось**.

Кратко: OCR переведён с EasyOCR на системный движок Windows. Сборка стала **20 раз
легче** (938 МБ → 45 МБ папка, ZIP 22,3 МБ), распознавание — **в 35–50 раз быстрее**,
EasyOCR остался в исходниках и включается одной настройкой.

### 1.1 `brain/ocr_providers/win_ocr.py`

Интерфейс специально сделан EasyOCR-совместимым, чтобы не трогать цикл захвата:

```python
ocr = WinOCR()
ocr.read_text(image_path_or_pil)     # -> str          (основной метод)
ocr.extract_text(image)              # -> str          (как brain.ocr_engine.OCREngine)
ocr.readtext(image, detail=0)        # -> ["строка", ...]  (как easyocr.Reader.readtext)
ocr.readtext(image, detail=1)        # -> [([[x,y]*4], "строка", 0.9), ...]
```

Внутри — два бэкенда с автоматическим откатом:

1. **`winrt`** (пакеты `winrt-*`, pywinrt) — основной путь: `Windows.Media.Ocr`
   в том же процессе, 17–40 мс на кадр.
2. **`powershell`** — запасной: тот же движок через Windows PowerShell 5.1
   (`powershell.exe -File`), результат пишется в UTF-8-файл (обход «кракозябр» и
   ограничений WinRT-проекции PS 5.1: индексаторы `Lines[0]`/`Words[0]` там не
   работают, обход только через `foreach`). ~0,45 с на кадр — медленно, но
   работает, даже если `winrt` не встал (например, для новой версии Python ещё нет
   колеса `winrt-runtime`).

Полезные детали:
- вход: PIL-картинка, путь к файлу, байты, numpy-массив, `None` (→ `""`);
- **апскейл мелких кадров** до ~1000 px по длинной стороне (Lanczos): на тексте
  13–15 px (а VN-шрифты именно такие) это убирает потерю пунктуации
  (`kid` → `kid.`, `breaks _` → `breaks.`);
- кадры больше лимита движка (10000 px) уменьшаются;
- `warmup()` — прогрев движка на пустом кадре: первый реальный кадр из буфера
  обрабатывается без задержки;
- `is_available()` / `available_recognizer_languages()` — диагностика языковых
  пакетов.

### 1.2 `main.py`

- `_create_ocr(settings)` — единая точка выбора провайдера. Импорт ленивый:
  `brain.ocr_engine` грузится **только** при `"ocr_provider": "easyocr"`.
- Отсутствие EasyOCR ловится как `ImportError` и превращается в понятное сообщение
  («…в сборке Lightweight нет easyocr и torch. Установите: pip install easyocr или
  переключитесь на Windows OCR: `"ocr_provider": "windows"`»), а не в трейсбек
  `ModuleNotFoundError: No module named 'easyocr'`.
- Если Windows OCR недоступен — попытка откатиться на EasyOCR (если он стоит).
- В журнале при старте: `Используется OCR: Windows Native`, затем язык и бэкенд.

### 1.3 Настройки

В `data/settings.json` появился ключ (по умолчанию `windows`):

```json
{ "ocr_provider": "windows" }
```

Значение `easyocr` возвращает старый движок; мусор в поле санитизируется до
`windows`. Есть переменная окружения `GADGET_OCR_PROVIDER` (как у остальных
настроек).

### 1.4 Сборка

`requirements.txt`: убраны `easyocr`, `torch`, `torchvision`; добавлены
`winrt-runtime`, `winrt-Windows.Media.Ocr`, `winrt-Windows.Graphics.Imaging`,
`winrt-Windows.Storage.Streams`, `winrt-Windows.Globalization`,
`winrt-Windows.Foundation`, `winrt-Windows.Foundation.Collections`, `pystray`.

Флаги PyInstaller: `--collect-all winrt`, `--hidden-import winrt.windows.{media.ocr,
graphics.imaging,storage.streams,globalization}` и обязательные
`--exclude-module easyocr/torch/torchvision/torchaudio/cv2/scipy/numpy/skimage/
matplotlib/pandas`. **Без исключений PyInstaller снова подтянул бы torch**:
`main.py` хоть и импортирует `brain.ocr_engine` лениво, анализ байткода видит
`import easyocr` внутри функции и тянет всю цепочку.

Сборка проверяет себя сама: до PyInstaller — что импортируются `winrt`, Pillow и
CustomTkinter; после — что в бандле есть `winrt\windows\media\ocr` и нет
`torch`/`easyocr`/`torchvision`. При ошибке скрипт останавливается с понятным
сообщением и ждёт Enter (раньше окно закрывалось мгновенно). Чистятся только
`build\`, `dist\GadgetOfTheFuture\` и прошлый ZIP этого релиза — архивы прошлых
версий больше не удаляются.

### Что поправлено после независимого ревью

Перед сдачей код прошёл отдельное ревью (отдельный агент, только чтение). По его
находкам исправлено:

| Было | Стало |
| --- | --- |
| Первое же исключение навсегда переключало OCR на PowerShell, второе — отключало совсем | пауза бэкенда только после 3 ошибок подряд (30 с), успех сбрасывает счётчик, `last_error` хранит причину |
| Пустой кадр («текста нет») запускал PowerShell (~0,5 с на кадр) | пустой ответ winrt — валидный, фоллбэк только по исключению |
| Ошибка запуска OCR — только в журнале, окно мигало | карточка с причиной в оверлее |
| Пустой ответ PowerShell считался успехом | обязательный маркер `{"ok":true}`, иначе ошибка |
| `WinOCR(backend="bogus")` тихо отключал OCR | `ValueError` при создании |
| `Image.open` держал файл открытым до сборщика мусора | `with` + `load()`, дескрипторы не копятся |
| `max_width` принимался и не использовался | применяется при подготовке кадра |
| Сборка удаляла весь `dist\` и не показывала ошибки при двойном клике | точечная чистка, проверки до/после PyInstaller, пауза на ошибках |
| Список провайдеров дублировался в `settings.py` | единый `PROVIDERS`, регистр нормализуется |

Не исправлено намеренно (вынесено в roadmap): замок состояния OCR на несколько
потоков (сейчас OCR вызывается из одного потока), очистка «осиротевших»
`gadget_ocr_*` в `%TEMP%` после жёсткого kill, инициализация COM-apartment только
в реально используемой ветке.

## 3. Отступления от задания (и почему)

1. **`build.bat` → ASCII-обёртка над `build.ps1`.** Причина техническая:
   `cmd.exe` разбирает bat-файл в текущей кодовой странице консоли, а строка
   `chcp` **внутри** файла сбивает смещение повторного чтения. На файлах больше
   ~4,5 КБ это ломает многострочную команду PyInstaller
   (`'--name' is not recognized as an internal or external command`). Проверено
   экспериментом: тот же файл без `chcp` — 0 ошибок, с `chcp` — ошибка, и это не
   зависит от кодировки самого файла. Все флаги PyInstaller (убрать
   `--collect-all torch/easyocr/torchvision`, добавить `--collect-all winrt`) на
   месте, только в `build.ps1`; `build.bat` остался точкой входа — двойной клик
   работает как раньше.
2. **Добавлены `winrt-Windows.Storage.Streams`, `winrt-Windows.Globalization`,
   `winrt-Windows.Foundation`, `winrt-Windows.Foundation.Collections`** — без них
   путь «картинка → SoftwareBitmap → OcrEngine» не собрать.
3. **`numpy` исключён из сборки** (в `requirements.txt` оставлен): он был нужен
   только EasyOCR. Экономия — десятки мегабайт.
4. **Добавлен `tests/test_win_ocr.py`** — чтобы регрессия «Windows OCR не работает
   в собранном exe» ловилась тестами, а не пользователем.

## 4. Риски и известные ограничения beta

| Риск | Влияние | Что делать |
| --- | --- | --- |
| Нет языкового пакета OCR `en-US` | Windows OCR не стартует, откат на EasyOCR, которого в сборке нет → понятная ошибка в журнале | Инструкция в README есть; в v1.5.1 — проверка и подсказка в лаунчере |
| `winrt-runtime` привязан к версии Python (сейчас `cp314`) | При переходе на Python 3.15 колеса может не быть | Есть PowerShell-фоллбэк (0,45 с/кадр); версию Python фиксировать в README/CI |
| Windows OCR не оценивает уверенность | `detail=1` отдаёт заглушку `0.9` | Никто её сейчас не использует; если понадобится фильтр — брать длину строки/словарь |
| Стилизованные/рукописные шрифты VN | Возможны пропуски, движок не умеет поворачивать текст | Апскейл уже есть; следующий шаг — препроцессинг (контраст/бинаризация) и сравнение на реальных кадрах |
| Vertical text / CRT-эффекты | Не распознаёт | Ограничение движка, не лечится на нашей стороне |
| `pystray` в зависимостях, но не используется | +0 к размеру (не импортируется), путаница | Либо сделать трей-иконку (см. roadmap), либо убрать из requirements |
| `build.ps1` требует разрешения на запуск скриптов | У части пользователей `ExecutionPolicy` блокирует | В `build.bat` уже `-ExecutionPolicy Bypass` |
| Спека `GadgetOfTheFuture.spec` | Не в git, генерируется PyInstaller'ом и удаляется при сборке — мёртвая конфигурация | Удалить или сделать единственным источником флагов |

## 5. Как развивать дальше

### 5.1 Приоритет 0 — до публикации v1.5.0

1. **Проверка OCR в лаунчере.** Сейчас провайдер переключается только правкой
   `settings.json`. Нужен экран «OCR: Windows Native / EasyOCR» с кнопкой
   «Проверить OCR» (распознать тестовую картинку и показать текст) — это снимет
   80 % проблем «у меня не работает».
2. **Понятная ошибка про языковой пакет** в оверлее/лаунчере со ссылкой
   `ms-settings:regionlanguage` + подсказкой, как поставить `en-US`.
3. **Прозрачность релиза:** в README — что Windows OCR ≠ EasyOCR по качеству на
   стилизованных шрифтах, и что делать, если нужно вернуть EasyOCR.
4. **Проверить на реальных кадрах** (5–10 скриншотов из разных VN): если качество
   просядет, добавить препроцессинг — grayscale + autocontrast + лёгкий
   `median`-фильтр, порог по средней яркости; это 20 строк и замер до/после.

### 5.2 Приоритет 1 — качество и UX перевода

- **Захват области вместо `Win+Shift+S`**: глобальный хоткей → рамка → автоматическое
  разпознавание. Это убирает два лишних шага у пользователя и главную точку отказа
  (забыл скопировать в буфер).
- **Кэш переводов** по хешу распознанного текста (`data/translate_cache.json`):
  повторяющиеся реплики VN («...», «Да.», «Хорошо.») не будут дёргать модель.
- **Стриминг Ollama** (`stream: true`) — перевод начнёт появляться в оверлее через
  200–400 мс вместо 1–3 с.
- **Батчинг**: копить 2–3 реплики и переводить одним запросом (меньше накладных
  расходов на локальную модель).
- **Второй лёгкий OCR как опция**: `rapidocr-onnxruntime` (~80 МБ, кросс-платформенный,
  часто лучше на игровых шрифтах) — подключается тем же `ocr_provider`, что уже
  сделан расширяемым (`PROVIDERS` в `brain/ocr_providers/__init__.py`).

### 5.3 Приоритет 2 — инженерия и поставка

- **CI (GitHub Actions)**: `unittest` + сборка PyInstaller на `windows-latest` +
  проверка, что ZIP < 100 МБ и что в бандле нет `torch`. Сейчас регрессию «сборка
  потяжелела» ловит только человек.
- **Убрать мёртвый `GadgetOfTheFuture.spec`** или, наоборот, сделать его
  единственным источником флагов (PyInstaller понимает `.spec` лучше, чем длинную
  командную строку).
- **Иконка и версия в exe** (`--icon`, `--version-file`), сейчас у exe нет ни того,
  ни другого.
- **Трей-иконка** (pystray уже в зависимостях): пауза, показать/скрыть, выход без
  окна лаунчера.
- **Метрики в журнал**: время OCR, время перевода, промахи — это дешёвый способ
  понять, где тормозит, без телеметрии.
- **Легаси `gadget9.py`** (старый скрипт с EasyOCR) — перенести в `legacy/` или
  удалить: сейчас он сбивает с толку и ломает `pip install -r`-ожидания.

### 5.4 Приоритет 3 — дальше по продукту

- **Портативный режим** (данные рядом с exe уже поддерживаются; нужен
  `--portable`-флаг в лаунчере и упаковка без установщика).
- **Автообновление** (проверка версии на GitHub Releases + скачивание ZIP) —
  сейчас обновление вручную.
- **Кроссплатформенность**: Windows OCR привязан к Windows; для Linux/macOS
  понадобится `rapidocr`/`tesseract` — архитектура провайдеров это уже позволяет.
- **Локальная модель по умолчанию**: `translategemma:4b` даёт хороший результат, но
  стоит замерить `qwen2.5:3b` на 100 репликах и выбрать по скорости/качеству.

## 6. Что нужно от тебя (проверка перед публикацией)

1. Запустить `dist\GadgetOfTheFuture\GadgetOfTheFuture.exe` **без** прав
   администратора, проверить оверлей на своей игре (оконный/безрамочный режим).
2. Сделать 5–10 скриншотов реальных VN-диалогов и сравнить с EasyOCR-версией — если
   где-то хуже, дай кадры, добавлю препроцессинг.
3. Сказать, нужен ли трей и выбор OCR в лаунчере — сделаю в v1.5.1 (или сразу, если
   это блокер).
4. Решить судьбу `pystray` и `GadgetOfTheFuture.spec`.
